# Архитектура модуля «Домены» и связка двух ТЗ

Документ фиксирует, **как две части ТЗ становятся одним софтом**, и почему
границы модулей проведены именно так.

## 1. Две части — две стадии одного отбора

Оба ТЗ описывают отбор доменов из большого микс-списка, но с разных осей:

| | Часть 1 — Ahrefs-фильтр | Часть 2 — Классификатор по имени |
|---|---|---|
| **Ось** | Авторитет / спам (ссылочный профиль) | Смысл названия (тематика + язык) |
| **Источник** | Выгрузка Ahrefs Batch Analysis | Строка-домен (textarea / мост) |
| **Решает** | Формулы (чистая функция) | Нейросеть (OpenAI/OpenRouter) |
| **Внешние API** | нет | да |
| **Выход** | тиры A/B/C/Review/Rejected | good / bad / на проверку |

Часть 1 в своём ТЗ **явно отказывается** от классификации по имени и от
гео/тематики — это «вне компонента». Часть 2 ровно это и делает. Значит, они не
конкурируют, а стыкуются: сначала дёшево и локально отсекаем мёртвый/спамный
мусор по ссылкам, затем дорогой LLM-проверкой чистим выживших по названию.

## 2. Мост

Точка стыковки — **список `Target`**.

```
Часть 1 → rows[] с полем Target и tier
        → пользователь выбирает тиры (по умолчанию A,B,C)
        → POST /api/ahrefs/datasets/{id}/targets?tiers=A,B,C
        → ["site1.com/", "site2.net/", …]
        → Часть 2: textarea предзаполняется этими доменами
```

На фронте состояние моста живёт в `App.tsx` (`bridgedTargets`); кнопка в
`AhrefsView` вызывает `onBridge`, панель переключается на вкладку «Классификатор»,
`ClassifierView` подхватывает домены. Бэкенд-эндпоинт `targets` переиспользует
тот же чистый пайплайн — никакой отдельной логики отбора.

Почему список доменов, а не богатый объект: Часть 2 по ТЗ судит **только по
имени** и сама нормализует ввод (снимает схему/www/путь). Передавать метрики
Ahrefs туда незачем — это разные оси. Если позже понадобится сквозной отчёт
(тир + вердикт), объединение делается по нормализованному домену как ключу.

## 3. Одна панель, одна вкладка настроек

Требование заказчика: «один софт, одна фронтенд-панель, одна вкладка настроек».

- **Панель** (`App.tsx`) — сайдбар с вкладками: Ahrefs-фильтр, Классификатор,
  Настройки, История и логи.
- **Одна вкладка «Настройки»** с двумя секциями-переключателями:
  - **Scoring (Ahrefs)** — веса, cap-константы, пороги отсева, границы тиров,
    флаги; живая валидация; пресеты (общий механизм на весь модуль).
  - **AI (Классификатор)** — провайдер/ключи/модель/Batch/порог confidence
    (каркас; наполняется в Части 2).
- **Общий конфиг** держится в состоянии панели, чтобы правки в «Настройках»
  мгновенно отражались на результатах Части 1 (живой пересчёт).

## 4. Почему бэкенд Части 1 — чистая функция

ТЗ-1 §9 требует пересчёт при смене параметров **без повторной загрузки**.
Реализация: `loader` один раз парсит и нормализует строки в `DomainRecord`,
которые лежат в `DatasetStore` (память, привязка к сессии). `analyze(records,
config)` не трогает сеть и не пишет состояние — повторный вызов с новым конфигом
дёшев. Пресеты и (в Части 2) история/логи персистятся в SQLite на volume.

## 5. Границы, зафиксированные из ТЗ

- Часть 1 **не** экспортирует из Ahrefs и по своему ТЗ получает «уже загруженные
  строки». Практически панель обязана принять файл, поэтому чтение файла (обе
  формы экспорта) вынесено в `loader.py` — тонкий «мост форматов» на входе,
  отделённый от чистого ядра.
- Часть 1 **не** делает гео/тематику — только выдаёт сырьё (`cc`, `tld`,
  `flag_geo_review`, `flag_cjk`).
- Часть 2 **не** имеет локальных словарей и не детектит язык кодом — это делает
  модель; софт лишь оркестрирует (батчи, ретраи, схема, раскладка).

## 6. Дальнейшие шаги (Часть 2)

1. Абстракция провайдера (OpenAI-совместимый `base_url`+`model`+`api_key`).
2. Батчинг (`batch_size` 50), concurrency, ретраи на 429/5xx/таймаут.
3. Фиксированная внутренняя инструкция + JSON-схема ответа (валидация).
4. Раскладка good/bad/review по фиксированным правилам (§6 ТЗ-2), порог
   confidence из настроек.
5. Кэш по нормализованному домену, инкрементальная история и логи (SQLite),
   resume после обрыва, оценка стоимости (учёт Batch −50%).
6. Экран «История и логи».
