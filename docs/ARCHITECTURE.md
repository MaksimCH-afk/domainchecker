# Архитектура модуля «Домены» и связка двух ТЗ

Документ фиксирует, **как две части ТЗ становятся одним софтом**, и почему
границы модулей проведены именно так.

## 1. Две части — две стадии одного отбора

Оба ТЗ описывают отбор доменов из большого микс-списка, но с разных осей:

| | Часть 1 — Ahrefs-фильтр | Часть 2 — Классификатор по имени |
|---|---|---|
| **Ось** | Авторитет / спам (ссылочный профиль) | Смысл названия (тематика + язык) |
| **Источник** | Выгрузка Ahrefs Batch Analysis | Строка-домен (textarea / мост) |
| **Решает** | Формулы (чистая функция) | Нейросеть (OpenAI/OpenRouter) |
| **Внешние API** | нет | да |
| **Выход** | тиры A/B/C/Review/Rejected | good / bad / на проверку |

Часть 1 в своём ТЗ **явно отказывается** от классификации по имени и от
гео/тематики — это «вне компонента». Часть 2 ровно это и делает. Значит, они не
конкурируют, а стыкуются: сначала дёшево и локально отсекаем мёртвый/спамный
мусор по ссылкам, затем дорогой LLM-проверкой чистим выживших по названию.

## 2. Мост

Точка стыковки — **список `Target`**.

```
Часть 1 → rows[] с полем Target и tier
        → пользователь выбирает тиры (по умолчанию A,B,C)
        → POST /api/ahrefs/datasets/{id}/targets?tiers=A,B,C
        → ["site1.com/", "site2.net/", …]
        → Часть 2: textarea предзаполняется этими доменами
```

На фронте состояние моста живёт в `App.tsx` (`bridgedTargets`); кнопка в
`AhrefsView` вызывает `onBridge`, панель переключается на вкладку «Классификатор»,
`ClassifierView` подхватывает домены. Бэкенд-эндпоинт `targets` переиспользует
тот же чистый пайплайн — никакой отдельной логики отбора.

Почему список доменов, а не богатый объект: Часть 2 по ТЗ судит **только по
имени** и сама нормализует ввод (снимает схему/www/путь). Передавать метрики
Ahrefs туда незачем — это разные оси. Если позже понадобится сквозной отчёт
(тир + вердикт), объединение делается по нормализованному домену как ключу.

## 3. Одна панель, одно окно, одна вкладка настроек

Требование заказчика: «один софт, одна фронтенд-панель; оба инструмента в одном
окне без переключения вкладок».

- **Панель** (`App.tsx`) — светлая тема, оба инструмента (**Ahrefs-фильтр** и
  **Классификатор**) отрисованы на одной прокручиваемой странице, друг под
  другом, разделённые «мостом». Никаких вкладок для переключения между ними.
- **Настройки** и **История и логи** — выезжающие панели (drawer) по кнопкам в
  шапке, чтобы не засорять рабочее окно.
- **Одна вкладка «Настройки»** с тремя секциями-переключателями:
  - **Scoring (Ahrefs)** — веса, cap-константы, пороги отсева (вкл. `dr_floor` и
    опциональный `spam_floor_reject`), границы тиров, флаги; живая валидация;
    пресеты.
  - **AI (Классификатор)** — провайдер, **выбор модели** (дефолт `gpt-4.1-mini` +
    резервы), Batch, параметры прогона. Модель — только для классификатора
    (анализатор нейросеть не использует).
  - **Ключ OpenAI** — ввод, сохранение и **проверка** ключа (тест к провайдеру).
- **Общий конфиг** Части 1 держится в состоянии панели, чтобы правки мгновенно
  отражались на результатах (живой пересчёт). AI-настройки персистятся на бэке.
- **Таблицы результатов** — собственная область прокрутки с залипающей шапкой,
  ограниченной своим блоком (не «выезжает» в соседний инструмент).
- **Порт 43784** (nginx слушает его же, без маскировки на :80).

## 4. Почему бэкенд Части 1 — чистая функция

ТЗ-1 §9 требует пересчёт при смене параметров **без повторной загрузки**.
Реализация: `loader` один раз парсит и нормализует строки в `DomainRecord`,
которые лежат в `DatasetStore` (память, привязка к сессии). `analyze(records,
config)` не трогает сеть и не пишет состояние — повторный вызов с новым конфигом
дёшев. Пресеты и (в Части 2) история/логи персистятся в SQLite на volume.

## 5. Границы, зафиксированные из ТЗ

- Часть 1 **не** экспортирует из Ahrefs и по своему ТЗ получает «уже загруженные
  строки». Практически панель обязана принять файл, поэтому чтение файла (обе
  формы экспорта) вынесено в `loader.py` — тонкий «мост форматов» на входе,
  отделённый от чистого ядра.
- Часть 1 **не** делает гео/тематику — только выдаёт сырьё (`cc`, `tld`,
  `flag_geo_review`, `flag_cjk`).
- Часть 2 **не** имеет локальных словарей и не детектит язык кодом — это делает
  модель; софт лишь оркестрирует (батчи, ретраи, схема, раскладка).

## 6. Реализация Части 2 (классификатор по имени)

Реализовано и покрыто тестами:

1. **Абстракция провайдера** — единый OpenAI-совместимый клиент
   (`base_url`+`model`+`api_key`) для OpenAI и OpenRouter; провайдер `mock`
   для офлайн-демо/тестов (`providers.py`).
2. **Оркестрация прогона** (`engine.py`) — батчинг (`batch_size` 50),
   concurrency через `asyncio.Semaphore`, ретраи с экспоненциальной задержкой
   на 429/5xx/таймаут, один повтор на битый JSON, затем `error`; отмена;
   инкрементальная запись каждого пакета (устойчивость к обрыву, NFR-2).
3. **Фиксированная инструкция + JSON-схема** (`instruction.py`, `schema.py`) —
   инструкция developer-owned, не редактируется пользователем; ответ
   валидируется и коэрцится, домены сопоставляются обратно по имени (FR-9/10).
4. **Раскладка good/bad/review** — фиксированные правила **по вердикту**
   (`buckets.py`, см. Корректировки ниже): `error`→Review, `bad`→Bad,
   `good`→Good. Язык и confidence на бакет не влияют.
5. **Кэш, история, логи, стоимость** — SQLite на volume (`store.py`): кэш по
   нормализованному домену (FR-12), история прогонов, логи INFO/DEBUG, оценка
   стоимости с учётом Batch −50% (`cost.py`, NFR-3). Ключи маскируются,
   не пишутся в логи/историю (NFR-4).
6. **UI** — экран «Проверка» (три бакета, прогресс, отмена, копирование,
   экспорт, языковой фильтр в «На проверку»), рабочая AI-секция настроек,
   экран «История и логи».

### Асинхронная модель прогона

Прогоны на 5k–50k доменов длинные, поэтому старт возвращает `run_id`, а бэкенд
исполняет прогон фоновой `asyncio`-задачей; фронтенд опрашивает
`GET /runs/{id}` (прогресс + инкрементальные бакеты) и может отменить.

### Batch API

Скидка −50% учтена в оценке стоимости (`cost.estimate_cost`), а флаг `batch_api`
проброшен в прогон. Полный асинхронный файловый Batch-workflow (submit → poll →
retrieve, до 24 ч) — отдельная надстройка над тем же движком; синхронный
concurrent-путь реализован полностью и является рабочим по умолчанию.

## 7. Корректировки (аддендумы к ТЗ, приоритет над исходными пунктами)

По результатам тестовых прогонов применены правки:

**Классификатор:**
- Раскладка — **строго по вердикту** (`buckets.py`): язык имени и `confidence`
  убраны из раскладки, остались справочными колонками. Чистое имя на любом языке
  → Good; порог confidence удалён из настроек и логики. Добавлен опциональный
  флаг модели `needs_review` → На проверку.
- Инструкция (`instruction.py`) усилена: распознавание категорийных терминов
  внутри склеенных строк, со снятием аффиксов и транслитом (`wangdai`=网贷),
  бренды препаратов (`avana`/`avanafil`), расширены лексиконы pharma/
  crypto_finance; защита от ложных срабатываний (`cialico`≠cialis). `confidence`
  переопределён как уверенность в вердикте (не `0.00` для решённого вердикта).

**Анализатор:**
- Новое обязательное правило `dr_floor` (`reject.py`): REJECT если `DR < dr_min`,
  дефолт `0.5` — ловит DR=0 с наполненным ссылочным, что проскакивало dead/thin.
- Опциональное `spam_floor_reject` (тумблер, по умолчанию выключено).

**Модель:**
- Дефолт классификатора `gpt-4.1-mini`, резервы `gpt-4.1-nano` / `gpt-5.4-mini` /
  `gpt-5.4-nano` (список от бэкенда + ручной ввод). Селектор — только у
  классификатора; анализатор остаётся чистой математикой без модели.
- Приёмочные списки A/B из корректировок проверяются только на реальной модели
  (офлайн-`mock` тонкие кейсы транслита/брендов не воспроизводит).
